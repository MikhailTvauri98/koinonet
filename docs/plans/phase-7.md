# Фаза 7. Редизайн по утверждённому макету

> Исполнение: по прямому указанию заказчика от 01.11.2026 — **одна задача — один субагент**; уточнение от 06.11.2026 разрешает до трёх независимых исполнителей параллельно в изолированных рабочих копиях. Это исключение для фазы 7 из прежнего порядка AGENTS.md: координатор ведёт весь план, каждый исполнитель получает одну задачу, не создаёт вложенных помощников или ревьюеров и не переходит к следующей. Зависимости задач соблюдаются; координатор сам проверяет требования, диф и результаты тестов, возвращает исправления тому же исполнителю и принимает/объединяет результаты последовательно. В каждой задаче сначала падающий тест, затем минимальная реализация и рефакторинг с повторным запуском тестов.

**Цель:** внедрить утверждённый графитовый интерфейс с синим акцентом и тёмной темой по умолчанию; исправить сценарии участников, форм, выбора и чатов; приоритетно сделать удобными календарь, создание и просмотр событий.

**Архитектура:** существующие Nuxt SPA/Vue/Pinia, Laravel API, общие CSS-токены и семантические элементы. Никакой замены UI-фреймворка или переноса демонстрационного приложения. Серверные изменения ограничены предпросмотром кандидатов свободного слота; остальные задачи используют существующие контракты.

**Стек:** зависимости из `apps/web/package.json` и `apps/api/composer.json`, Vitest/Vue Test Utils, Playwright, Pest, ESLint, Nuxt typecheck, Pint, PHPStan.

**Спецификация:** [утверждённый дизайн](../design/phase-7/spec.md), [отдельный аудит календаря](../design/phase-7/calendar-audit.md). Начать с обоих документов и затрагиваемых разделов архитектуры 4–7/10; задача 7 также читает раздел 8.

**Статус:** планирование выполнено 01.11.2026; заказчик поручил координатору исполнение задач отдельными субагентами. Дизайн одобрен пользователем в этом чате с заменой зелёного на синий. Дополнительный запрос на проверку календаря включён в задачи 4–8 и 20. Состояние реализации фиксируется чекбоксами и отчётами задач ниже.

## Общие ограничения

- Одна задача — 1–3 часа, самостоятельный проверяемый результат отдельного субагента. При превышении объёма разбить остаток в плане, закончить текущую часть с зелёными проверками. Один исполнитель не получает следующую задачу; координатор продолжает план после проверки результата без повторного запроса разрешения.
- Ветки `phase-7/task-N-slug`; база каждой задачи — проверенное состояние всех её зависимостей. Независимые задачи могут выполняться параллельно (до трёх исполнителей) в изолированных рабочих копиях; результаты принимаются и объединяются координатором последовательно. Пока есть несогласованная смесь старого/нового интерфейса, промежуточный редизайн не вливается в `main`: там включена автоматическая выкладка. Финальная PR в `main`, squash — после задачи 20.
- Тексты и бизнес-понятия — `CONTEXT.md`; проверки — ключами прав и серверными `can_manage`/`can_fill`, не названиями ролей. Модульные границы, архив, UTC и часовой пояс церкви сохраняются.
- Палитра — точные значения спецификации; никаких зелёных брендовых акцентов. Основной текст 16 px, вторичный 14 px; области нажатия от 44 px; текст 200% не уменьшается обратно.
- Тёмная тема по умолчанию, явный выбор светлой сохраняется на устройстве. Без новой настройки сервера, внешних шрифтов, CDN или нового набора UI-зависимостей.
- Демонстрация не отменяет множественные роли, полную навигацию, права на персональные данные, существующие виды повторения, iCal, приглашения и административные действия.
- Не маскировать ошибки общим `overflow-x:hidden`, не обновлять снимки автоматически без просмотра отличий. Не выдавать наличие скриншота или зелёную геометрию за эстетическую приёмку.
- Все локальные пути `app/`, `tests/`, `public/`, `e2e/` и конфиги ниже — относительно `apps/web/`. `apps/api/` и `docs/` указаны от корня репозитория. Каждый пункт «Файлы» дополнительно включает этот план и затронутый раздел `docs/architecture.md`.
- Данные прототипа не попадают в начальные данные, фикстуры production или интерфейс. Название церкви читается из settings.

## Общий цикл проверки задачи

1. Записать RED-тест конкретного нового поведения; запустить его и сохранить причину падения. Старый инвариант не удалять ради нового вида.
2. Реализовать минимум, получить GREEN; после рефакторинга повторить профильные тесты.
3. Из `apps/web`: `npm run test -- --maxWorkers=1`, `npm run lint`, `npm run typecheck`. При изменении CSS/клиента: `npm run generate`, `npm run verify-sw`. Результаты команд и существующие предупреждения привести в отчёте задачи.
4. Запустить указанный профильный Playwright-набор: `npm run test:visual -- tests/visual/<file>.pw.ts`. На Windows допустим установленный Edge через `E2E_BROWSER_CHANNEL=msedge`; сервер и браузер должны видеть один localhost. В отчёте указать фактический браузер.
5. Просмотреть снимки затронутых экранов в обеих темах на 390 и 1440 px, проверить узкую ширину/длинные данные. Новые тесты геометрии добавлять только на поведение или реальный риск регрессии.
6. При изменении API — проверки задачи 7, а не только клиентские фикстуры. Проверки не зависят от production-данных.
7. Саморевью дифа: границы модулей; ключи прав вместо имён ролей; термины словаря; обновлённые документы. Отметить чекбоксы только после фактических проверок и сделать коммит задачи.

## Особое внимание при ревью

1. Другой часовой пояс устройства, переход месяца/года, событие через полночь: даты и личные назначения остаются правильными — задачи 4–8.
2. Поздний поиск, смена аккаунта/служения и отзыв прав при открытом выборе: старые данные не появляются вновь — задачи 7, 9–14.
3. Длинные русские имена, 200% текста, короткий мобильный экран и клавиатура: действия не пропадают — задачи 2–6, 12, 14, 20.
4. Закрытое localStorage, ошибочная тема, обновление PWA: первый кадр остаётся корректным — задачи 1, 20.
5. Ошибка отправки, успешная запись с неудачным перечитыванием, повтор нажатия: ввод и подтверждённый результат не теряются, нет дублей — задачи 5–8, 10–11, 14–19.
