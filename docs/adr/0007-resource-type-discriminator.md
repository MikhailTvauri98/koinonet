# Дискриминатор `resource_type` вместо универсальной таблицы ресурсов

Заказчик хочет позже добавить помещения и технику как ресурсы событий, но сейчас нужны только люди. Принято: у слота и назначения есть поле `resource_type` с единственным пока значением `person`, а ссылки на конкретные ресурсы хранятся в типизированных nullable-колонках с внешними ключами (`person_id` сейчас, `room_id` и другие позже) под check-ограничением «заполнена ровно та колонка, что соответствует типу». Таблица `people` остаётся таблицей людей со своей предметной логикой, а не строкой в абстрактной таблице `resources`.

## Рассмотренные варианты

- Универсальная таблица `resources` с типом и JSON-атрибутами. Отклонено: люди теряют богатую модель (аккаунт, роли, контакты), а атрибуты уходят в EAV.
- Полиморфная связь без внешних ключей (`resource_type` + `resource_id`). Отклонено: теряется ссылочная целостность ради одного будущего типа.

## Последствия

- Колонка с одним возможным значением выглядит избыточной, это сделано намеренно: добавление помещений станет миграцией с новой колонкой и новым значением enum, без переписывания календаря.
- Требование слота тоже типизировано: для людей это `role_id`, для помещений появится своя колонка.
